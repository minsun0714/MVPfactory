## 1. 제품 정의

MVP 팩토리는 사용자가 사이드 프로젝트 아이디어와 CEO 개입 수준을 입력하면, 가상의 제품팀 에이전트들이 기획·디자인·개발·검증을 진행하고 사용자의 GitHub와 Vercel에 작은 Next.js 웹앱을 완성하는 서비스다. 데이터 저장이 필요한 앱에는 DB를 자동으로 구성한다. 사용자는 배포 결과에 피드백을 주어 같은 프로젝트를 수정·재배포할 수 있다.

첫 MVP의 목표는 **에이전트들이 실제 앱을 만들고, 필요한 DB를 연결하고, 배포한 뒤 기존 데이터를 유지하며 수정하는 전체 흐름과, 캐릭터 꾸미기·사무실 확장·회의 애니메이션을 포함한 가상 회사 경험**을 함께 제공하는 것이다.

데모 실행과 정해진 예시 산출물은 개발 중 흐름 검증에 사용할 수 있다. 실제 LLM 작업, 코드 생성, 데이터 저장, 저장소 반영, 배포를 대신하는 MVP 완료 증거로 사용하지 않는다.

이 문서는 제품의 목표 행동을 정의한다. 현재 코드의 구현 여부, 구체적인 프레임워크·모델·API 계약·DB 스키마는 코드 확인과 후속 설계에서 결정한다.

## 2. 결정 상태와 적용 원칙

| 구분             | 내용                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 사용자 확정 요구 | 아이디어 입력, 역할별 에이전트 협업, 가상 스타트업과 CEO 참여 경험                                                          |
| 사용자 확정 요구 | 생성 앱은 Next.js를 사용하며 사용자의 GitHub에 저장소를 생성하고 코드를 push한 뒤 Vercel에 배포                             |
| 사용자 확정 요구 | 프로젝트 시작 시 CEO 개입 수준 선택                                                                                         |
| 사용자 확정 요구 | 첫 버전부터 필요한 앱의 가벼운 DB 자동 생성·연결 지원                                                                       |
| 사용자 확정 요구 | 고급 캐릭터 꾸미기, 사무실 확장, 복잡한 회의 애니메이션을 첫 MVP의 핵심 기능으로 포함                                       |
| 사용자 확정 요구 | 이번 MVP에서는 팩토리와 생성 앱의 로그인을 구현하지 않음                                                                    |
| 사용자 확정 요구 | GitHub·Vercel·DB 계정은 공통 기본 설정에 미리 등록하고 프로젝트마다 재입력 없이 사용                                        |
| 제품 흐름에 포함 | 같은 프로젝트에 대한 피드백 반영과 데이터 보존을 전제로 한 재배포                                                           |
| PRD 기본안       | 작은 개인용 웹 도구, 생성 앱의 주요 화면 1~3개                                                                              |
| PRD 기본안       | DB 공급자는 Supabase 하나로 시작, 생성 앱별 새 프로젝트 사용                                                                |
| PRD 기본안       | CEO 레벨은 위임형·핵심 결정형·공동 설계형, 기본 선택은 핵심 결정형                                                          |
| PRD 기본안       | 단일 사용자 작업 공간에서 동시 실행 하나, 새 GitHub 저장소는 private를 기본 선택으로 제안                                   |
| 별도 결정        | 모델과 AI 연결 방식, 생성 코드 실행 환경, 사용량 수치와 요금 정책(팩토리 기술 스택과 공통 설정의 저장 방식은 §2.1에서 확정) |

PRD 기본안은 구현을 구체화하기 위해 제안한 정책이다. 사용자 확정 사항으로 소급해서 표현하지 않는다. 변경이 필요하면 이유와 영향을 기록하며, 기존에 허용된 작업을 동일한 내용으로 반복 승인받도록 만들지 않는다.

생성 앱에 Next.js를 사용하는 요구와 팩토리 자체의 기술 선택을 구분한다. LangGraph, Prisma, 특정 LLM, 특정 SKILL.md는 이 PRD의 필수 제품 요구사항이 아니다.

## 3. 해결할 문제와 대상 사용자

### 3.1 문제 가설

사이드 프로젝트를 만드는 개발자는 구현 능력이 있어도 아이디어 구체화, 기능 범위 결정, 화면 설계, 코딩 도구에 반복 지시하기, DB와 배포 연결, 후속 수정 관리에 부담을 느낄 수 있다.

MVP 팩토리는 이 과정을 하나의 프로젝트 흐름으로 연결하고 이미 결정한 내용을 유지하여, 사용자가 직접 조율하고 수습하는 시간을 줄이는 것을 목표로 한다. 기존 도구보다 편리하거나 완성도가 높다는 주장은 실제 비교 전까지 가치 가설로 취급한다.

### 3.2 핵심 대상

아래 페르소나는 초기 사용자 탐색을 위한 가상 사례다.

| 페르소나                          | 상황과 어려움                                                       | 기대하는 가치                                                 |
| --------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------- |
| 김도윤, 개발 3년 차 백엔드 개발자 | 작은 아이디어는 있지만 화면 구성과 기획에 시간을 쓰다가 완성을 미룸 | 필요한 제품·디자인 판단을 보완받고 실제 사용 가능한 앱을 완성 |
| 박서연, 개발 6년 차 풀스택 개발자 | 코딩 에이전트 사용 경험이 있고 여러 아이디어를 빠르게 확인하고 싶음 | 반복 지시와 검토 부담을 줄이면서 자신의 저장소에서 후속 개발  |

초기 우선 대상은 코딩 에이전트를 사용해 봤으며, 기획·화면 결정·반복 지시의 부담을 경험한 개인 개발자다.

### 3.3 핵심 사용자 과업

“만들고 싶은 아이디어와 내가 관여할 수준을 정하면 팀이 작은 앱을 완성하고, 결과에 피드백을 주면 이전 결정을 유지한 채 다음 버전으로 이어가게 하고 싶다.”

## 4. 목표와 MVP 범위

### 4.1 제품 목표

- 아이디어를 구현 가능한 기능·화면·데이터·완료 조건으로 구체화한다.
- 실제로 동작하는 작은 Next.js 앱과 사용자 소유 코드를 제공한다.
- 필요한 DB 연결과 배포 설정을 사용자가 프로젝트마다 수동으로 조립하는 부담을 줄인다.
- 선택한 CEO 개입 수준에 따라 검토 시점을 조절한다.
- 같은 프로젝트의 결정·코드·DB를 유지하면서 후속 변경을 반영한다.
- 고급 캐릭터 꾸미기와 사무실 확장으로 나만의 가상 회사를 구성하고, 회의 애니메이션으로 실제 협업과 결정 과정을 관전할 수 있게 한다.

### 4.2 생성 앱의 첫 지원 범위

| 영역        | 첫 MVP 범위                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------- |
| 사용 목적   | 개인 기록, 목록 관리, 정리, 간단한 계산·계획                                                                          |
| 화면        | 주요 화면 1~3개를 기본으로 기획                                                                                       |
| 기능        | 입력 검증, 생성·조회·수정·삭제, 단순 검색·필터, 간단한 계산                                                           |
| 데이터      | 필요하면 DB를 생성하고 영속 저장. 저장 요구가 없는 앱에는 불필요한 DB를 생성하지 않음                                 |
| 인증        | 이번 MVP에서는 로그인·회원가입을 구현하지 않음. 로그인이나 사용자별 비공개 데이터가 핵심인 앱은 지원 범위 밖으로 안내 |
| 코드와 배포 | 새 GitHub 저장소와 Next.js 앱, Vercel 배포                                                                            |
| 후속 작업   | 팩토리가 만든 동일 프로젝트의 기능 수정과 비파괴적 DB 변경                                                            |

주요 화면 1~3개는 생성 앱의 기본 규모이며 팩토리 자체 화면 수를 제한하는 규칙이 아니다. 핵심 요구가 지원 범위를 넘으면 가능한 범위와 차이를 제시하고 선택을 받는다. 핵심 기능을 조용히 생략하지 않는다.

### 4.3 첫 MVP에서 제외하는 범위

- 임의의 기존 GitHub 저장소를 가져와 분석·수정하는 기능.
- 여러 DB 공급자, 기존 운영 DB 이전, 복잡한 데이터 마이그레이션.
- 모바일 네이티브 앱과 다양한 생성 프레임워크.
- 생성 앱의 결제, 복잡한 조직 권한, 실시간 공동 편집, 임의의 외부 API 통합.
- 여러 사용자의 공동 CEO 참여와 조직 관리.
- 실행 도중 세부 승인 규칙을 편집하거나 CEO 레벨을 전환하는 기능.
- 팩토리와 생성 앱의 로그인·회원가입, 다중 사용자 인증과 사용자별 권한 관리.
- 자동 시장 검증, 사용자 수요나 수익의 보장.
- 대규모 자동 평가 플랫폼, 파인튜닝, 여러 모델의 자동 비용 최적화.

고급 캐릭터 꾸미기, 사무실 확장, 복잡한 회의 애니메이션은 실제 작업 관전과 함께 첫 MVP의 필수 범위다. 단순 역할 아이콘이나 상태 표시만으로 완료 처리하지 않는다.

## 5. 핵심 사용자 흐름

1. 사용자가 로그인 없이 단일 사용자 작업 공간을 열고 프로젝트를 시작한다.
2. 아이디어, 목적이나 제약, CEO 개입 레벨을 입력한다.
3. 공통 설정에 미리 등록한 기본 GitHub·Vercel·DB 계정을 자동으로 사용하고, 적용되는 실행 대상·공개 범위·실행 한도를 확인한다. 프로젝트 생성 시 계정 입력이나 연결을 반복하지 않는다.
4. 팀이 지원 가능 범위를 확인하고 기능·화면·데이터·완료 조건을 작성한다.
5. 선택한 CEO 레벨에 해당하는 지점에서 검토하거나 위임받은 판단으로 진행한다.
6. 개발 에이전트가 코드를 작성하고 필요한 DB를 자동 구성한다.
7. 빌드와 핵심 기능을 검증하고 허용된 한도에서 오류를 수정한다.
8. 사용자 GitHub에 코드를 반영하고 Vercel 배포 결과를 확인한다.
9. 사용자는 배포 앱, 코드, 검증 결과를 확인하고 피드백을 입력한다.
10. 같은 프로젝트·저장소·DB·배포 대상에서 변경을 반영하고 다시 검증·배포한다.

외부 계정과 기본 실행 대상·공개 범위·실행 한도는 프로젝트와 분리된 공통 설정에서 미리 등록·관리한다. 새 프로젝트는 이 설정을 자동으로 사용한다. 미설정·권한 만료·철회 시에만 공통 설정 수정을 안내한다. 기본 계정을 변경해도 기존 프로젝트의 저장소·DB·배포 대상을 자동 교체하지 않는다.

사용자는 가상 회사에서 캐릭터를 꾸미고 사무실을 확장하며, 팀의 회의와 작업을 관전할 수 있다. 꾸미기와 공간 설정은 재접속 후에도 유지한다.

## 6. CEO 개입 정책

아래 세부 정책은 PRD 기본안이다. 레벨은 제품 의사결정의 참여 수준을 정하며, 기본 품질 검사와 접근 보호 수준은 모든 레벨에서 동일하다.

| 항목                  | 레벨 1 위임형                          | 레벨 2 핵심 결정형      | 레벨 3 공동 설계형                      |
| --------------------- | -------------------------------------- | ----------------------- | --------------------------------------- |
| 기능과 화면 방향      | 팀이 선택하고 기록                     | 기능·화면 통합안을 검토 | 기능 범위 검토 후 화면 방향을 별도 검토 |
| 예정된 중간 검토 지점 | 없음                                   | 구현 전 1개 지점        | 기능과 화면의 2개 지점                  |
| 세부 구현과 검증      | 자동 진행                              | 확정안에 따라 자동 진행 | 확정안에 따라 자동 진행                 |
| DB·저장소·배포 작업   | 시작 시 허용한 대상과 범위 안에서 진행 | 동일                    | 동일                                    |
| 배포 후 피드백        | 제공                                   | 제공                    | 제공                                    |

- 기본 선택은 핵심 결정형이다.
- 검토 지점 수는 질문 횟수의 상한이 아니다. 해당 지점에서 사용자의 수정 요청을 반영할 수 있다.
- 사용자가 답하지 않으면 대기를 유지한다. 시간 경과를 승인으로 간주하지 않는다.
- 권한 부족, 범위 변경, 사전 설정한 한도 초과 등 필요한 결정이 생기면 모든 레벨에서 구체적인 선택을 요청한다.
- 이미 위임한 동일 작업을 반복 승인받지 않는다.
- 사용자의 확정 요구사항을 바꾸는 결정과 에이전트가 정할 수 있는 세부 선택을 구분해 기록한다.
- 현재 실행의 레벨은 유지한다. 다음 수정 실행에서는 레벨을 다시 선택할 수 있다.
- 사용자는 전체 대화를 읽거나 계속 관전하지 않아도 작업을 이어갈 수 있다.

## 7. 기능 요구사항과 수락 조건

이 절의 요구사항은 첫 기능 MVP의 P0 범위다. 각 요구사항의 현재 구현 상태는 미확인이며, 실제 코드와 실행 결과로 판정해야 한다.

### REQ-001 프로젝트 생성과 지원 범위 확인

사용자는 아이디어, 선택적인 목적·제약, CEO 레벨을 입력해 프로젝트를 생성하고 나중에 다시 열 수 있다.

- **AC-001-1:** 저장 후 재접속하면 원본 아이디어, 단일 사용자 작업 공간, CEO 레벨, 확정 요구사항을 동일하게 조회할 수 있다.
- **AC-001-2:** 필수 입력이 없거나 형식이 잘못되면 이유를 설명하고 생성 요청을 처리하지 않는다.
- **AC-001-3:** 지원 범위를 넘는 핵심 요구가 있으면 차이와 가능한 대안을 표시하며, 사용자 선택 없이 핵심 요구를 삭제하지 않는다.

### REQ-002 공통 기본 계정과 실행 설정

GitHub·Vercel·DB 계정과 실행 대상·공개 범위·실행 한도를 공통 설정에 미리 등록한다. 모든 새 프로젝트는 저장된 기본 설정을 재사용한다.

- **AC-002-1:** 연결됨·미연결·권한 부족·연결 해제 상태를 구분해 표시한다. 필요한 연결이 없으면 해당 외부 작업을 성공 처리하지 않는다.
- **AC-002-2:** 외부 리소스 생성과 변경은 해당 사용자에게 허용된 계정·조직·프로젝트 범위에서 수행한다.
- **AC-002-3:** 로그인 없이 동일한 단일 사용자 작업 공간을 사용하며, 프로젝트 생성마다 외부 계정이나 비밀값을 다시 입력하도록 요구하지 않는다.
- **AC-002-4:** 연결이 해제·철회되면 그 권한으로 새 외부 작업을 진행하지 않고, 진행 상태와 공통 설정에서 필요한 다음 행동을 표시한다.
- **AC-002-5:** 공통 설정 변경은 이후 새 프로젝트에 적용한다. 기존 프로젝트는 저장된 외부 리소스 참조를 유지하고, 접근 권한이 사라지면 차단 사유를 표시한다.
- **AC-002-6:** 서로 다른 프로젝트 두 개를 생성해 같은 기본 계정을 재입력 없이 사용하는지 확인한다. 각 프로젝트의 저장소·DB·배포 리소스는 별도로 추적한다.

### REQ-003 CEO 검토와 응답 반영

선택한 레벨에 따라 검토 지점을 적용하고, 사용자의 응답과 수정 내용을 이후 작업에 반영한다.

- **AC-003-1:** 위임형은 예정된 중간 검토 없이 진행하고, 핵심 결정형과 공동 설계형은 6절의 지정 지점에서 대기한다.
- **AC-003-2:** 사용자 응답 없이 검토가 승인되거나 다음 단계로 넘어가지 않는다.
- **AC-003-3:** 수정 후 확정한 기능과 화면 방향이 공통 프로젝트 요구사항과 후속 작업 입력에 반영된다.
- **AC-003-4:** 같은 응답을 중복 제출해도 동일 결정이 두 번 반영되거나 후속 실행이 중복 생성되지 않는다.

### REQ-004 기획 산출물과 결정의 연속성

기획 역할은 아이디어를 대상 사용자, 목적, 핵심 기능, 제외 범위, 데이터, 화면, 완료 조건으로 구체화한다.

- **AC-004-1:** 산출물에 핵심 목적·기능·데이터·완료 조건이 포함되고, 사용자 확정 사항과 에이전트 가정이 구분된다.
- **AC-004-2:** 디자인과 개발 역할이 같은 버전의 확정 요구사항과 결정 기록을 사용한다.
- **AC-004-3:** 근거 없는 시장 조사, 수요, 사용자 인터뷰를 실제 수행한 사실처럼 제시하지 않는다.
- **AC-004-4:** 변경된 결정은 이전 내용과 변경 이유를 확인할 수 있다.

### REQ-005 생성 앱의 화면 설계

디자인 역할은 핵심 과업을 수행할 수 있는 화면 구성과 사용 흐름을 정의한다.

- **AC-005-1:** 핵심 기능마다 사용자가 시작하고 결과를 확인하는 화면 또는 동작이 연결되어 있다.
- **AC-005-2:** 데이터가 없는 상태, 로딩, 입력 오류, 저장 실패의 필요한 동작과 표시가 정의되어 있다.
- **AC-005-3:** 최종 앱의 주요 화면에서 핵심 버튼·폼·탐색이 실제 기능에 연결된다. 동작하지 않는 요소를 완료 기능으로 제시하지 않는다.
- **AC-005-4:** 데스크톱과 모바일 크기의 화면에서 핵심 과업을 수행할 수 있고, 입력 요소의 이름과 상태를 식별할 수 있다.

### REQ-006 실제 코드 생성과 실행

개발 역할은 확정된 요구사항과 화면 구성을 반영하는 실행 가능한 Next.js 앱을 생성한다.

- **AC-006-1:** 실제 프로젝트 파일이 생성되며, 개발 계획이나 예시 텍스트만으로 구현 완료를 표시하지 않는다.
- **AC-006-2:** 생성 코드를 프로젝트별 실행 환경에서 설치·빌드·실행하고 실제 결과를 확인할 수 있다.
- **AC-006-3:** 실행·빌드·기능 검증에서 발견된 오류를 정해진 한도 내에서 수정하고 결과를 기록한다.
- **AC-006-4:** 모델이나 도구 연결이 없으면 해당 기능을 미연결·실패·차단으로 표시한다. 실제 실행을 데모 결과로 조용히 대체하지 않는다.

### REQ-007 생성 앱의 DB 자동 구성

데이터 저장이 필요한 앱에는 공통 기본 DB 계정과 범위 설정을 사용해 DB 생성부터 앱 연결까지 자동화한다. 첫 공급자는 Supabase를 기본안으로 한다.

- **AC-007-1:** DB 필요 여부와 이유가 기획에 기록된다. DB가 불필요한 앱에는 DB를 의무적으로 생성하지 않는다.
- **AC-007-2:** 필요한 앱은 연결된 조직에 DB 프로젝트 생성, 준비 상태 확인, 스키마·제약조건·접근 규칙 적용, 앱 환경 설정을 자동으로 수행한다.
- **AC-007-3:** 사용자가 프로젝트마다 연결값과 비밀값을 복사해 붙여 넣지 않아도 데이터 기능이 동작한다. 권한·한도 문제는 필요한 사용자 행동과 함께 표시한다.
- **AC-007-4:** 합의한 데이터 생성·조회·수정·삭제와 재접속 후 조회를 실제 DB로 확인한다.
- **AC-007-5:** 이번 MVP는 로그인과 사용자별 데이터 분리를 생성하지 않는다. 로그인이나 비공개 개인 데이터 보호가 핵심 요구이면 지원 범위 밖임을 안내하고, 사용자 선택 없이 해당 요구를 생략하지 않는다.
- **AC-007-6:** 연결 실패를 숨기기 위해 브라우저 저장이나 샘플 데이터로 전환하지 않는다. 팩토리 운영 DB와 생성 앱 DB의 상태를 구분해 표시한다.

### REQ-008 사용자 GitHub에 코드 제공

공통 설정에 등록한 기본 GitHub 계정 또는 조직에 새 저장소를 생성하고 실제 앱 소스를 반영한다.

- **AC-008-1:** 해당 사용자에게 허용된 대상에 저장소가 생성되고, 코드가 실제 커밋으로 존재한다.
- **AC-008-2:** 결과 화면에서 저장소 URL과 현재 결과에 해당하는 커밋을 확인할 수 있다.
- **AC-008-3:** 비밀 키·토큰·DB 비밀번호는 커밋에 포함하지 않는다. 필요한 설정 이름과 실행 방법은 문서로 제공한다.
- **AC-008-4:** 저장소 생성이나 push가 실패하면 완료된 단계와 실패한 단계를 구분한다.

### REQ-009 Vercel 배포와 결과 접근

생성 앱을 공통 설정에 등록한 기본 Vercel 대상에 배포하고, 실제 결과를 확인할 수 있는 URL을 제공한다.

- **AC-009-1:** 배포의 성공 상태와 접근 가능한 결과를 확인한 뒤 실제 URL을 제공한다.
- **AC-009-2:** 배포된 소스 버전을 GitHub의 해당 커밋과 연결해 확인할 수 있다.
- **AC-009-3:** 저장소 공개 범위와 앱 접근 범위를 별도로 표시하고, 실행에 적용된 기본 범위 안에서 배포한다. 적용할 수 없는 설정은 사용자 선택 없이 다른 범위로 대체하지 않는다.
- **AC-009-4:** 배포 결과에서 핵심 사용 흐름과 필요한 DB 동작을 확인한다. 배포 요청 접수만으로 성공을 표시하지 않는다.

### REQ-010 가상 회사 관전과 진행 표시

사용자는 PM·기획자·디자이너·개발자 역할의 현재 작업과 결과를 이해할 수 있다.

- **AC-010-1:** 역할별 대기·작업 중·완료·실패 상태가 실제 실행 상태와 연결된다.
- **AC-010-2:** 현재 단계, 최근 작업 결과, 주요 결정, CEO 응답 필요 여부를 긴 대화 전체를 읽지 않아도 파악할 수 있다.
- **AC-010-3:** 캐릭터나 애니메이션의 표시만으로 실제 진행 상태를 변경하지 않는다.
- **AC-010-4:** 데모 실행은 별도로 표시하며 실제 생성·배포 완료와 시각적·문구상으로 구분한다.

### REQ-011 요구사항 검증과 완료 판정

확정된 완료 조건별로 실행 결과를 확인하고 사용자에게 근거를 제공한다.

- **AC-011-1:** 필수 완료 조건을 통과·실패·미검증으로 나누고, 실행 결과 또는 재현 가능한 확인 근거를 연결한다.
- **AC-011-2:** 빌드 통과, 배포 성공, 제품 요구사항 충족을 별도로 표시한다.
- **AC-011-3:** 필수 기능에 실패·미검증 항목이 남으면 전체 제품 완료로 표시하지 않는다. 확인 가능한 중간 산출물은 별도로 제공할 수 있다.
- **AC-011-4:** 실행 결과가 확인되지 않았는데 에이전트의 “완료”라는 서술만으로 통과 처리하지 않는다.

### REQ-012 피드백 반영과 데이터 보존

사용자는 배포된 프로젝트에 자연어 피드백을 남기고 같은 프로젝트의 다음 버전을 받을 수 있다.

- **AC-012-1:** 수정 실행은 이전 요구사항·결정·코드·DB 구조를 이어받으며 변경 범위를 기록한다.
- **AC-012-2:** 같은 GitHub 저장소, 생성 앱 DB, Vercel 프로젝트를 사용한다. 새 프로젝트로 다시 만드는 동작으로 대체하지 않는다.
- **AC-012-3:** 필드 추가 등 합의된 변경 후 기존 기록과 유지 대상 기능이 보존된다.
- **AC-012-4:** 기존 데이터 삭제나 손실 가능성이 있는 변경이 사전 허용 범위를 넘으면 영향과 선택지를 제시하며 자동으로 진행하지 않는다.
- **AC-012-5:** 수정 결과를 다시 검증하고 커밋·배포 버전·변경 내용을 확인할 수 있다. 실패하면 마지막 정상 결과와 새 실행의 실패 내용을 확인할 수 있다.

수정·재배포 1회는 MVP의 최소 종단 검증 조건이다. 사용자에게 피드백을 한 번만 허용한다는 상품 제한이 아니다.

### REQ-013 일시정지와 실패 후 재개

사용자는 기존 작업을 다시 열고, 중단·실패한 실행을 상태에 맞게 이어갈 수 있다.

- **AC-013-1:** 새로 접속하거나 작업 프로세스를 재시작해도 확정 요구사항, CEO 응답 대기, 완료 단계, 외부 리소스 참조가 유지된다.
- **AC-013-2:** 일시정지 요청은 중단 가능한 지점에서 반영하고, 이미 시작된 외부 작업이 있으면 그 상태를 표시한다.
- **AC-013-3:** 재시도 시 이미 생성한 저장소·DB·배포 대상을 재사용한다.
- **AC-013-4:** 외부 작업 요청 후 응답을 받지 못해 성공 여부가 불명확하면 실제 상태를 확인한 뒤 재개한다. 확인 없이 중복 생성하지 않는다.
- **AC-013-5:** 재개할 수 없는 경우 원인과 필요한 다음 행동을 표시하며 완료된 산출물을 보존한다.

### REQ-014 실행 한도와 사용량 표시

사용자는 실행에 적용되는 제한과 현재 사용량을 이해할 수 있다.

- **AC-014-1:** 실행 시작 전에 적용할 반복 횟수·시간·비용 정책과 대상 범위를 표시한다. 수치는 별도 결정한다.
- **AC-014-2:** 한도에 도달하면 추가 작업 발행을 제한하고 현재 산출물, 남은 작업, 사용자가 선택할 행동을 표시한다.
- **AC-014-3:** 사용량에 추정치가 포함되면 추정임을 표시한다. 확인되지 않은 외부 비용을 확정 금액으로 제시하지 않는다.
- **AC-014-4:** 에이전트 실행 비용과 생성한 DB·호스팅 리소스의 지속 비용을 구분한다.
- **AC-014-5:** 일시정지·실패를 이유로 사용자의 기존 저장소나 데이터를 자동 삭제하지 않는다. 실행 중인 외부 요청은 공급자가 허용하는 중단 범위와 실제 결과를 표시한다.

### REQ-015 고급 캐릭터 꾸미기와 사무실 확장

사용자는 캐릭터의 외형을 조합하고 사무실 공간을 확장·배치하여 자신만의 가상 회사를 구성한다. 첫 MVP의 필수 기능이다.

- **AC-015-1:** 캐릭터의 외형·헤어·의상·액세서리를 조합하고 미리보기와 적용을 할 수 있다. 이름이나 색상만 바꾸는 기능으로 대체하지 않는다.
- **AC-015-2:** 사무실 영역을 확장하고 책상·회의 공간·장식의 배치를 변경할 수 있으며, 변경이 실제 가상 회사 화면에 반영된다.
- **AC-015-3:** 꾸미기와 확장·배치 상태를 저장하고 재접속 후 동일하게 복원한다.
- **AC-015-4:** 외형과 공간을 변경해도 역할 식별, 진행 상태 확인, CEO 응답과 실행 재개가 가능하다.

### REQ-016 실제 협업과 연결된 회의 애니메이션

역할별 캐릭터가 회의 공간으로 이동하고 착석·발언·반응·해산하는 다단계 애니메이션으로 팀의 협업을 표현한다. 첫 MVP의 필수 기능이다.

- **AC-016-1:** 회의 시작부터 이동·착석·발언자 전환·참여자 반응·해산까지 이어지는 장면을 제공한다. 단순 로딩 표시로 대체하지 않는다.
- **AC-016-2:** 참여 역할, 발언 요약, 검토 주제와 결정 결과가 실제 작업 이벤트와 연결되며 수행하지 않은 회의를 실제 작업처럼 표시하지 않는다.
- **AC-016-3:** CEO 응답 대기·실패·중단 상태를 장면에 반영하고, 회의 종료는 실제 결정·작업 상태와 일치한다.
- **AC-016-4:** 애니메이션을 건너뛰거나 동작을 줄여도 요약·결정 내용을 확인할 수 있고 실행 결과와 승인 상태는 동일하다.

## 8. 화면 요구사항

| 화면          | 핵심 정보와 동작                                                                                         | 필요한 예외 상태                             |
| ------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 프로젝트 목록 | 프로젝트 이름, 최근 상태, 최근 수정 시각, 새 프로젝트, 기존 작업 열기                                    | 프로젝트 없음, 조회 실패                     |
| 공통 설정     | 기본 GitHub·Vercel·DB 계정 등록·변경, 기본 대상·공개 범위·한도 관리                                      | 미설정, 권한 만료·철회, 저장 실패            |
| 프로젝트 시작 | 아이디어, 선택적인 목적·제약, CEO 레벨, 자동 적용된 기본 계정·대상·공개 범위·한도 요약                   | 입력 오류, 미연결, 권한 부족, 지원 범위 초과 |
| 가상 스타트업 | 캐릭터 꾸미기, 사무실 확장·배치, 회의 애니메이션, 현재 단계, 작업 요약, 산출물, 결정 응답, 일시정지·재개 | CEO 대기, 실패, 한도 도달, 연결 해제         |
| 결과와 개선   | 앱 URL, GitHub·커밋, 요구사항별 검증, DB 상태, 변경 내역, 피드백                                         | 부분 완료, 배포 실패, 필수 항목 미검증       |

화면은 실제로 구현된 기능에만 활성 동작을 제공한다. 미구현 기능은 이유와 함께 비활성 또는 미지원으로 표시한다. 제품 이용 화면에 내부 프레임워크·도구 설정을 불필요하게 노출하지 않으며, 사용자의 판단에 필요한 연결·권한·비용·결과는 명확히 제공한다.

구체적인 색상, 타이포그래피, 컴포넌트 스타일은 후속 디자인 문서에서 정한다.

## 9. 상태와 완료의 의미

아래는 사용자에게 전달할 의미를 정의하며, 실제 코드의 enum이나 DB 필드명을 강제하지 않는다.

| 상태          | 의미                                              | 사용자에게 필요한 정보                   |
| ------------- | ------------------------------------------------- | ---------------------------------------- |
| 대기          | 실행이 접수되어 시작을 기다림                     | 대상 프로젝트, 적용한 설정               |
| 진행 중       | 기획·개발·검증·배포 중 하나를 수행                | 현재 단계와 최근 결과                    |
| CEO 응답 대기 | 지정된 검토 지점에서 사용자 결정 필요             | 제안, 선택 항목, 수정 방법               |
| 일시정지      | 사용자가 요청한 중단 가능한 지점에서 정지         | 완료 단계와 재개 방법                    |
| 차단          | 권한·설정·한도 등 실행 조건이 충족되지 않음       | 원인과 필요한 조치                       |
| 실패          | 허용된 시도 안에서 현재 실행 목표를 달성하지 못함 | 실패 단계, 보존된 결과, 재시도 가능 여부 |
| 완료          | 해당 실행의 필수 완료 조건을 실제로 통과          | 검증 근거와 결과물                       |

- **빌드 통과:** 코드가 빌드되었다는 의미다.
- **배포 성공:** 해당 버전의 배포가 성공하고 접근할 수 있다는 의미다.
- **제품 완료:** 합의한 필수 기능·데이터·접근·배포 조건까지 확인되었다는 의미다.
- **데모 완료:** 내부 모의 흐름이 끝났다는 의미이며 실제 제품 완료 지표에 포함하지 않는다.

예를 들어 배포 URL은 있으나 저장 기능이 실패하면 “배포 성공, 기능 검증 실패”로 보여준다. 전체 제품 완료로 바꾸지 않는다.

## 10. 실패 처리 정책

| 상황                                                | 필요한 행동                                                                |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| 아이디어의 핵심 요구가 지원 범위를 초과             | 가능한 범위와 차이를 설명하고 변경 선택을 받음                             |
| 모델 출력이 요구 형식이나 필수 항목을 충족하지 못함 | 한도 내에서 수정하거나 실패 내용을 표시하고 잘못된 결과의 전파를 막음      |
| 빌드·기능 검증 실패                                 | 실제 오류를 전달해 제한된 수정 수행, 해결되지 않으면 실패로 남김           |
| DB 생성 후 연결 실패                                | 생성한 DB와 적용 이력을 보존하고 연결 단계에서 재개                        |
| 저장소·DB 생성 후 배포 실패                         | 기존 리소스를 재사용하고 배포 실패를 별도로 표시                           |
| 외부 요청 결과 불명확                               | 공급자의 실제 상태를 조회한 뒤 다음 행동 결정                              |
| 계정 권한 철회·만료                                 | 필요한 작업을 차단하고 재연결 방법 표시                                    |
| 한도 도달                                           | 추가 작업을 제한하고 현재 결과와 남은 작업 제공                            |
| 수정 중 기존 데이터에 영향을 줄 수 있는 변경 발견   | 사전 허용 범위와 영향을 확인하고 필요한 선택 요청                          |
| 수정 실행 실패                                      | 마지막 정상 배포·커밋과 새 실패 실행을 구분하고 이미 적용된 DB 변경을 표시 |

외부 서비스 전반의 자동 원복을 보장한다고 표현하지 않는다. 실제로 적용된 변경과 남아 있는 영향을 확인할 수 있게 한다.

## 11. 품질과 운영 요구사항

### 11.1 데이터와 권한

- 이번 MVP는 로그인 없는 단일 사용자 작업 공간을 기준으로 하며 사용자별 접근 격리를 제공한다고 표시하지 않는다. 생성 앱은 로그인 없이 사용할 수 있는 범위에서 검증한다.
- 관리 비밀값은 GitHub, 브라우저 코드, 공개 로그, 대화, 모델 입력에 노출하지 않는다. 공개 가능한 설정값과 관리 비밀값을 구분한다.
- 생성 코드의 실행은 다른 프로젝트와 팩토리 운영 데이터에 접근하지 못하도록 제한한다.
- 검증용 데이터와 실제 사용자 데이터를 구분하며 검증 과정에서 기존 기록을 삭제하거나 덮어쓰지 않는다.

### 11.2 신뢰성과 관찰 가능성

- 프로젝트와 실행, 단계, 산출물, 결정, 외부 리소스의 관계를 추적할 수 있어야 한다.
- 실패 이유, 도구 실행 결과, 모델·지침 버전, 소요 시간과 확인 가능한 사용량을 기록한다. 비밀값과 불필요한 개인정보는 제외한다.
- 외부 부수 효과의 중복을 막을 수 있도록 실행 식별자와 리소스 참조를 보존한다.
- 서버 재시작과 화면 재접속은 이미 확정한 사용자 결정을 소실시키지 않는다.

### 11.3 사용자 경험과 성능

- 긴 작업은 현재 단계와 대기 이유를 표시하고, 제출 중 중복 실행을 방지한다.
- 지원하지 않는 기능, 미연결, 실패, 미검증을 서로 구분한다.
- 핵심 과업은 데스크톱과 모바일 크기에서 수행할 수 있어야 한다.
- 첫 버전의 지연 시간 목표와 사용량 상한은 실제 계측 후 설정한다. 근거 없이 “몇 분 안에 모든 앱 완성”을 보장하지 않는다.

## 12. 핵심 데이터 개념

구체적인 테이블과 관계는 후속 DB 설계에서 정한다.

| 개념                              | 저장 목적                                                      |
| --------------------------------- | -------------------------------------------------------------- |
| 단일 사용자 작업 공간과 공통 설정 | 기본 외부 계정, 대상·공개 범위·실행 한도와 외부 작업 권한 관리 |
| 가상 회사 설정                    | 캐릭터 외형·의상·액세서리, 사무실 확장·배치 상태 보존          |
| 프로젝트                          | 원본 아이디어, 확정 요구사항, 현재 결과의 연속성 유지          |
| 실행                              | 최초 생성과 각각의 수정·재시도 작업의 진행과 결과 관리         |
| 결정                              | CEO 검토 요청과 응답, 선택 이유, 변경 이력 보존                |
| 산출물                            | 기획·화면·코드·검증 결과의 버전과 참조 관리                    |
| 외부 리소스                       | GitHub 저장소·커밋, 생성 앱 DB, Vercel 프로젝트·배포 참조      |
| 사용량과 실행 이벤트              | 실패 분석, 비용·시간 확인, 품질 비교                           |

프로젝트 하나가 여러 실행을 가질 수 있다. 실제 코드는 작업 공간과 GitHub 등 적합한 저장 위치에서 관리하고, DB에는 필요한 식별자와 참조를 둘 수 있다. 모든 코드와 로그를 하나의 DB 필드에 저장해야 한다는 요구는 아니다.

## 13. MVP 검증 과제와 출시 기준

### 13.1 기준 앱

개인 공부 기록 앱을 기본 검증 과제로 사용한다.

- 기본 입력: 날짜, 제목, 메모.
- 기능: 로그인 없이 테스트 기록 생성·목록 조회·수정·삭제.
- 검증 데이터: 비공개 개인 정보가 아닌 테스트용 기록 사용.
- 데이터: 실제 DB 저장과 재접속 후 조회.
- 후속 요청: “공부 시간을 추가해줘.”
- 후속 완료 조건: 기존 기록을 유지하고 새 필드를 사용할 수 있으며 기존 기능도 유지.

이 과제는 검증용 대표 사례이며 서비스가 공부 기록 앱만 생성한다는 제품 제한은 아니다.

초기에는 비슷한 난도의 작은 과제로 검증 범위를 늘린다. 개발 중 모의 응답을 이용한 테스트는 가능하지만, 최초 생성과 수정 배포의 MVP 완료 판정에는 실제 DB·저장소·배포 결과가 필요하다.

### 13.3 첫 기능 MVP의 완료 조건

- [ ] 모든 P0 요구사항에 구현 위치와 검증 근거가 연결되어 있다.
- [ ] 기준 앱의 실제 최초 생성·배포가 성공한다.
- [ ] 최소 한 번의 피드백 반영과 데이터 보존 재배포가 성공한다.
- [ ] CEO 세 레벨의 검토 지점과 결정 반영을 확인한다.
- [ ] 중단·실패·한도 도달을 완료로 오인시키지 않는다.
- [ ] 로그인 없이 기본 계정을 재사용해 여러 프로젝트를 시작할 수 있다.
- [ ] 고급 캐릭터 꾸미기·사무실 확장·회의 애니메이션의 수락 조건을 충족한다.
- [ ] 실행한 검증 범위에서 기존 데이터 유실과 프로젝트 실행 환경 간 무단 접근이 없다.
- [ ] 미검증 항목과 환경 제약을 별도로 표시한다.
- [ ] 재접속과 프로세스 재시작 후 필요한 상태를 복원할 수 있다.

이는 제한된 범위의 첫 기능 MVP 완료 기준이다. 다양한 아이디어와 사용자 환경에 대한 신뢰도는 후속 평가와 실사용으로 확인한다.

### 13.4 외부 사용자 테스트 조건

이번 MVP는 로그인 없는 단일 사용자 환경에서 검증한다. 외부 사용자 3~5명의 평가는 각자 분리된 실행 환경과 미리 등록한 기본 계정을 사용하거나, 운영자가 진행하는 관찰 세션으로 수행한다. 공용 다중 사용자 서비스와 인증 도입은 후속 범위이며 첫 MVP의 완료 조건에 포함하지 않는다.

## 14. 성공 지표

초기 수치는 계측할 지표와 목표값을 구분한다. 아래 지표의 첫 측정값을 기준선으로 삼고, 근거 없이 성공률이나 시간 절감 수치를 확정하지 않는다.

| 지표                  | 측정 정의                                                                                  | 목적                              |
| --------------------- | ------------------------------------------------------------------------------------------ | --------------------------------- |
| 최초 앱 완료율        | 지원 범위 안에서 시작한 최초 생성 요청 중 필수 조건을 통과한 비율. 실패 요청도 분모에 포함 | 실제 완성 능력 확인               |
| 수정 완료율           | 시작한 수정 요청 중 기존 데이터와 유지 대상 기능을 보존하며 배포한 비율                    | 프로젝트 연속성 확인              |
| 사용자 직접 개입 시간 | 설명·검토·추가 지시·수동 수습에 사용한 시간                                                | 조율 부담 감소 확인               |
| 반복 설명 횟수        | 이미 전달·확정한 요구를 다시 설명해야 했던 횟수                                            | 요구사항 유지 능력 확인           |
| 시간과 비용           | 전체 경과 시간, CEO 응답 대기, 실제 처리 시간, 실패·재시도를 포함한 비용을 구분            | 개입 감소와 비용·대기의 균형 확인 |
| 후속 사용             | 결과 확인 후 실제 수정 또는 다른 프로젝트를 다시 맡기는지                                  | 지속적인 사용 가치 확인           |

자동 재시도를 별개의 성공 사례로 부풀리지 않는다. 취소·차단·데모는 별도 집계하고, 실패를 제외해 완료율을 높이지 않는다. 데이터 유실과 접근 위반은 별도의 결함으로 기록하며 화면 품질 점수로 상쇄하지 않는다.

가상 회사 경험은 이해도와 만족도를 함께 관찰하되, 재미에 대한 반응만으로 생산성이나 지불 의사가 검증됐다고 판단하지 않는다.

## 15. 기존 구현 개선에 적용하는 방법

1. 기존 저장소의 지침, 코드, 의존성, 실행 환경, 실제 화면을 확인한다.
2. 각 REQ를 구현 완료·부분 구현·미구현·검증 불가로 분류하고 근거를 기록한다.
3. 데모 산출물, 실제 연동, 비어 있는 어댑터를 구분한다.
4. 실제로 동작하는 기능을 보존하면서 결함 수정과 미구현 작업을 분리한다.
5. 각 작업에 관련 REQ·AC, 선행 조건, 수정 범위, 검증 방법을 연결한다.
6. 여러 코딩 에이전트가 작업하면 파일 소유권과 공통 계약 변경 담당을 후속 작업 문서에서 정한다.
7. 기능 추가 후 관련 수락 조건과 유지되어야 할 기존 기능을 확인한다.

이 PRD는 기존 코드의 문제 원인이나 완료 상태를 추정해 채우지 않는다. 전체 재작성 여부는 코드 확인 후 판단한다.
