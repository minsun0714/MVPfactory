# UX 원칙과 톤

> 최신 범위: 사용자 꾸미기·아이템 선택·사무실 확장·배치 편집은 제거했다. 고정 디자인의 사무실·캐릭터와 회의·생활 애니메이션을 유지한다. 이전 꾸미기 관련 제안은 폐기된 요구사항이다.

버전: 0.1 · 작성일: 2026-11-21  
적용 대상: UI·문구·인터랙션을 만드는 개발자와 코딩 에이전트.

이 문서는 제품이 "어떤 느낌이어야 하는지"를 정한다. 구체적인 값은 [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), 회의 장면은 [ANIMATION_SPEC.md](ANIMATION_SPEC.md)를 따른다. 제품 요구사항(REQ/AC)은 [MVP_FACTORY_PRD.md](MVP_FACTORY_PRD.md)가 우선한다.

**요약**

- 밝은 아이보리·월넛 갈색과 전체 픽셀 게임 UI. 팀원(에이전트)의 말투는 유머러스하다.
- 재미는 연출에만 쓴다. 완료·승인·실패는 서버가 알려 주는 사실만 보여 준다.
- CEO 결정 요청, 실패, 한도 도달 같은 중요한 순간에는 농담을 줄이고 정보를 먼저 쓴다.
- 모든 연출은 건너뛰거나 줄일 수 있어야 한다.

## 1. 한 줄 콘셉트

**"밝고 아기자기한 픽셀 스타트업에서, 유머러스한 팀원들이 내 아이디어로 진짜 앱을 만든다."**

## 2. 분위기 키워드

| 지향                                  | 지양                                     |
| ------------------------------------- | ---------------------------------------- |
| 아기자기한 픽셀아트, 레트로 게임 감성 | 차갑고 딱딱한 관리자 대시보드            |
| 밝은 아이보리, 월넛과 선명한 역할색   | 네온·글로우 위주의 어두운 개발자 도구    |
| 재치 있는 말투, 팀원들의 개성         | 과한 밈·비속어, 사용자를 놀리는 농담     |
| 한눈에 읽히는 상태와 다음 행동        | 장식 때문에 가려지는 진행 상태·결정 요청 |

### 2.1 확정된 사용 경험

아이소메트릭 사무실을 화면의 중심에 두고 캐릭터·알림을 누르면 중앙 업무 팝업을 연다. 승인 요청은 자동 팝업, 완료·오류는 작은 알림으로 표시한다. 헤더 없이 헤더 왼쪽에 홈으로 연결되는 로고·MVP 팩토리 이름, 그 옆에 프로젝트 선택창, 맨 오른쪽에 설정·알림 아이콘을 둔다. 모바일에서는 선택창을 다음 행에 배치한다. PM·기획자·디자이너·개발자 4명과 하나의 회사 설정을 모든 프로젝트가 공유한다. 캐릭터·사무실은 고정 디자인이며 첫 버전에는 소리가 없다. 에셋은 AI로 제작한 뒤 일관된 스타일과 동작으로 보정한다.

## 3. 핵심 원칙

1. **재미는 껍데기, 진실은 서버.** 캐릭터·애니메이션·농담은 분위기를 만든다. 완료·승인·실패 같은 실제 상태는 서버 값만 반영하고, 연출이 상태를 바꾸거나 앞질러 보여 주지 않는다. (AC-010-3, AC-016-2)
2. **가짜 성공 금지.** 데모·모의 실행은 항상 "데모"로 표시한다. 유머러스한 문구라도 수행하지 않은 일을 한 것처럼 쓰지 않는다. (AGENTS.md 불변 조건 1·2)
3. **중요한 순간에는 농담을 줄인다.** CEO 결정 요청, 실패, 한도 도달, 연결 해제, 데이터 보존 관련 안내는 먼저 명확하게 쓰고 재치는 한 문장 이내로 곁들인다.
4. **연출은 건너뛸 수 있다.** 모든 애니메이션은 건너뛰기·동작 줄이기를 지원하고, 같은 정보를 텍스트로 제공한다. (AC-016-4)
5. **역할과 상태는 일관되게 표시한다.** 고정 외형·이름표로 역할을 구분하고 진행 상태와 결정 응답 버튼을 쉽게 찾을 수 있게 한다.
6. **상태는 항상 네 가지를 설계한다.** loading, empty, error, pending(CEO 대기)에 각각 문구·시각 표현·다음 행동을 둔다.

## 4. 문구 톤 (유머러스)

### 4.1 기본 규칙

- 존댓말(해요체)을 쓴다. 반말·비속어·특정 집단을 비하하는 농담은 쓰지 않는다.
- 농담은 **팀원(에이전트)의 상황**에 대한 것이지 **사용자나 사용자의 아이디어**에 대한 것이 아니다.
- 한 화면에서 재치 있는 문구는 1~2곳으로 제한한다. 버튼·입력 라벨·오류 원인은 명확한 평서문으로 쓴다.
- 이모지는 상태 배지나 말풍선에서만 제한적으로 쓰고, 정보 전달을 이모지에만 맡기지 않는다.
- 문구는 한 곳(예: 문구 상수 모듈)에서 관리하고 컴포넌트에 흩어 쓰지 않는다.

### 4.2 역할별 말투

현재 `src/lib/roles.ts`의 역할을 기준으로 한다. 역할이 추가·변경되면 이 표를 함께 갱신한다.

| 역할     | 성격                       | 말투 예시                                                     |
| -------- | -------------------------- | ------------------------------------------------------------- |
| PM       | 일정에 예민한 조율자       | "마감은 내일입니다. 아니, 어제였을 수도 있습니다."            |
| 기획자   | 아이디어가 샘솟는 낙천가   | "기능이 하나 더 떠올랐는데… 아, 참을게요."                    |
| 디자이너 | 여백에 진심인 완벽주의자   | "이 버튼, 2px만 옮겨도 될까요? 아니, 영혼이 허락하지 않네요." |
| 개발자   | 무뚝뚝하지만 믿음직한 장인 | "빌드 돌렸습니다. 커피 한 잔 정도면 됩니다."                  |

## 5. 상호작용 원칙

- 한 화면의 주 행동은 하나로 두고, 보조·파괴적 행동은 시각적으로 구분한다.
- 결정 응답 폼은 결정 내용, 제안 버전, 선택지를 먼저 보여 주고 제출 후 결과(적용됨·충돌·이미 처리됨)를 명확히 알린다.
- 중복 클릭을 막고 제출 중 상태를 표시한다. 서버 응답 전에 승인·완료를 확정 표시하지 않는다.
- 새로고침·재접속 후 서버 상태에서 화면을 복원한다. 애니메이션은 현재 상태에 맞는 지점에서 이어 보여 주거나 요약으로 대체한다.
- 키보드만으로 모든 행동이 가능해야 하며 포커스 표시를 항상 보여 준다.

## 6. 접근성 기준

- 텍스트와 배경의 명도 대비는 WCAG AA(본문 4.5:1, 큰 글씨·UI 경계 3:1) 이상을 목표로 한다. 밝은 배경 위 글자는 어두운 색을 쓴다.
- 색만으로 상태를 구분하지 않는다. 아이콘·텍스트 라벨을 함께 쓴다.
- 픽셀 캐릭터와 장면에는 대체 텍스트 또는 텍스트 요약을 제공한다. 장식용 요소는 `aria-hidden`으로 숨긴다.
- 말풍선·상태 변화는 스크린 리더용 `aria-live` 영역에 텍스트로 전달한다.
- `prefers-reduced-motion: reduce`를 존중한다. 세부 규칙은 ANIMATION_SPEC.md를 따른다.

## 7. 아직 정하지 않은 항목

아래는 사용자 확정이 필요하다. 확정 전에는 기본 제안을 임시로 쓰고 코드에 임의로 굳히지 않는다.

- 서비스 마스코트·로고의 최종 형태
- 효과음·배경음은 첫 버전에서 제외하기로 확정했다. 남은 결정 항목이 아니다.
